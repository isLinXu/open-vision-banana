一、结论摘要

SparkLM 是一个功能极其丰富的小语言模型训练框架（MLA / MoE / MTP / VLM / Diffusion / 投机解码 / 专家并行 等），研究价值高、测试覆盖好（585+ 用例）。但当前的工程架构是“扁平堆叠”而非“分层设计”，且无法以标准方式 pip 安装。核心症结有三：

  • P0 四个并列顶层包污染全局命名空间：sparklm/、trainer/、dataset/、evaluation/、scripts/ 全部被打进 wheel，安装后会与用户环境里的同名模块冲突，pip install 后 import dataset 可能命中别人的包。
  • P0 HF 包装器引用了已不存在的 model.* 命名空间：modeling_sparklm.py / configuration_sparklm.py 里有 5 处 import_module("model.model_sparklm") 等回退路径，而 model/ 目录早已被重命名为 sparklm/ —— 这是历史重构遗留的死代码/隐患。
  • P1 分层缺失：模型层（model）、数据层（data）、训练层（train）、评测层（eval）、推理层（inference）、CLI 层混在同一层级，没有清晰的依赖方向；sparklm/__init__.py 用 268 行手写 __getattr__ 懒加载来弥补缺乏分层导致的导入开销。

整改方向：收敛为单一顶层包 sparklm/，内部按 models / data / training / eval / inference / cli / integrations 分层；用 src/ 布局 + 现代 pyproject.toml 实现干净的 pip install；HF 导出文件改为生成式产物而非源码根级文件。

三、问题逐项剖析

P0-1 · 多顶层包导致无法干净安装

pyproject.toml 显式声明：

[tool.setuptools.packages.find]
include = ["sparklm*", "dataset*", "trainer*", "evaluation*", "scripts*"]

这意味着 pip install sparklm 后，用户的 site-packages 里会出现顶层 dataset、trainer、scripts 模块。这些是极常见的通用名字，会与用户自己的代码或其它库直接冲突 —— 这是“不能直接 pip 安装”的根因。

判定：这不是写法瑕疵，而是打包契约错误。一个库只应暴露一个顶层命名空间。

P0-2 · HF 包装器引用已删除的 model.*

modeling_sparklm.py / configuration_sparklm.py 中：

# configuration_sparklm.py
try:
    from .config import SparkLMConfig as NativeSparkLMConfig   # 仅当作为包导入才成立
except ImportError:
    NativeSparkLMConfig = import_module("model.config").SparkLMConfig  # ← model/ 已不存在

项目历史上 model/ 已重命名为 sparklm/，但回退分支仍写 model.*（共 5 处）。当 transformers 通过 trust_remote_code 复制这些文件并以扁平方式加载时，from .config 会失败，回退到 model.config 又必然 ImportError。当前能跑只是因为恰好命中了第一分支，一旦导出路径变化即崩。

P1-3 · 缺乏分层，依赖方向混乱

理想的训练框架应是单向依赖金字塔：cli → training/eval/inference → models → core(components)。当前所有层平铺，且 sparklm/__init__.py 不得不用 268 行 __getattr__ 懒加载来避免“一次性 import 全家桶”的启动开销 —— 这正是分层缺失的代偿症状，而非好设计。

P1-4 · 巨石文件与 scripts 当包用

train_pretrain.py(49KB)、train_grpo.py(42KB) 单文件承担配置解析+数据装配+循环+评测+checkpoint。同时 scripts/ 既是 CLI 入口又被 from scripts.xxx import 当库引用（25 处），职责双重。脚本应通过 [project.scripts] entry-points 暴露，而非作为可导入包。

四、目标架构（src 布局 + 单一命名空间）

spark-git/ ├── pyproject.toml # 唯一构建契约，hatchling/setuptools src 布局 ├── README.md LICENSE Makefile ├── src/sparklm/ # ← 唯一顶层包 │ ├── __init__.py # 精简公共 API（保留懒加载但收敛） │ ├── core/ # 无依赖底座：RMSNorm/RoPE/工具/类型 │ ├── configs/ # config.py 拆分：base/presets/attention/moe/vlm │ ├── models/ # 纯模型实现 │ │ ├── attention/ # gqa / mla / saha / v4(csa,hca) │ │ ├── moe/ # moe_v4 / expert_parallel / kv_compression │ │ ├── feedforward.py components.py model_sparklm.py │ │ ├── mtp/ diffusion/ vision/ vlm/ │ │ └── kv_cache/ # cache + quant │ ├── data/ # ← 原 dataset/ 收进来 │ ├── training/ # ← 原 trainer/，按算法分子模块 │ │ ├── base.py utils.py │ │ ├── pretrain/ sft/ dpo/ grpo/ ppo/ vlm/ lora/ distill/ # 巨石拆分 │ │ └── optim/ # muonclip 等 │ ├── eval/ # ← 原 evaluation/ │ ├── inference/ # generation / speculative / profiling │ ├── integrations/ # 第三方桥接 + HF export │ │ └── hf/ # configuration/modeling/tokenization 模板 │ └── cli/ # ← 原 scripts/ 中的入口，entry-points ├── tests/ # 不打包 └── docs/ data/ results/ # 不打包

依赖规则（单向）：core ← configs ← models ← {training, inference, eval} ← cli。integrations 旁挂、可选。任何反向导入在 CI 用 import-linter 拦截。

五、可落地重构方案（分阶段）

阶段 0 · 仓库卫生（0.5 天，零风险）

动作说明
清理缓存/产物从工作区移除 .mypy_cache/ .ruff_cache/ .pytest_cache/ __pycache__/ .DS_Store .session_tmps/ output/ results/ 的误入文件，确认 .gitignore 已覆盖（已基本覆盖）。
固化测试基线跑全量 pytest 记录 585+ 绿，作为重构安全网。

阶段 1 · 单一命名空间 + src 布局（1–2 天，P0）

  • 新建 src/sparklm/，把现有 sparklm/* 移入；dataset/ → src/sparklm/data/，trainer/ → src/sparklm/training/，evaluation/ → src/sparklm/eval/，scripts/ → src/sparklm/cli/。
  • 全局改写导入：from dataset.→from sparklm.data.、from trainer.→from sparklm.training. 等（共 ~144 处，用脚本批量 + 测试验证）。
  • HF 三件套移入 src/sparklm/integrations/hf/，删除所有 import_module("model.*") 死分支，导出时由 export_hf.py 把模板拷到产物目录。

新的 pyproject.toml 关键段：

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[project]
name = "sparklm"
version = "0.4.0"
requires-python = ">=3.10"
dependencies = ["torch>=2.1.0","numpy>=1.24.0","tiktoken>=0.5.1",
                "transformers>=4.38.0","tqdm>=4.66.0"]

[project.optional-dependencies]
train = ["wandb>=0.16.0","accelerate>=0.26.0","datasets>=2.16.0","tensorboard>=2.14.0"]
eval  = ["rouge-score>=0.1.2","sacrebleu>=2.3.1"]
flash = ["flash-attn>=2.4.0"]
dev   = ["pytest>=7.4.0","pytest-timeout>=2.1.0","ruff>=0.4.0","mypy>=1.9.0,<2.2.0"]

[project.scripts]                       # scripts/ 改为命令行入口，而非可导入包
sparklm-train     = "sparklm.cli.train:main"
sparklm-eval      = "sparklm.cli.evaluate:main"
sparklm-infer     = "sparklm.cli.inference:main"
sparklm-export-hf = "sparklm.cli.export_hf:main"

[tool.hatch.build.targets.wheel]
packages = ["src/sparklm"]              # 只发布一个顶层命名空间

验证：pip install -e . 后 python -c "import sparklm; from sparklm.training import ...; sparklm-train --help" 全通过，且 site-packages 内不再出现 dataset/trainer/scripts。

阶段 2 · 内部分层与巨石拆分（2–4 天，P1）

  • models/ 下按 attention/ moe/ kv_cache/ 分子包，文件从平铺收进语义目录。
  • 拆分 config.py(39KB)→configs/{base,presets,attention,moe,vlm}.py；拆分 train_pretrain.py/train_grpo.py 为「config 解析 / 数据装配 / 训练循环 / 评测钩子」。
  • 抽象 BaseTrainer 模板方法，各算法 Trainer 继承，消除重复样板。
  • 收敛 __init__.py：按子包重导出，懒加载仅保留给真正重量级可选模块（flash-attn/vision）。

阶段 3 · 工程护栏（1 天，P2）

  • 引入 import-linter 在 CI 校验单向依赖；ruff 增加 TID(相对导入约束)。
  • 补 py.typed 标记，发布带类型信息的包。
  • README「安装」节统一为 pip install sparklm[train,eval]。

六、风险与收益

项评估
主要风险144 处跨包导入改写 + HF 导出路径变化。缓解：脚本化批量改写 + 585 用例回归 + 分阶段小步提交。
兼容性对外 API from sparklm import SparkLMForCausalLM, ... 保持不变；仅内部 dataset./trainer. 路径变化，影响下游脚本（提供迁移说明）。
收益① 可 pip install 且零命名空间污染；② 清晰分层、可独立测试每层；③ 巨石拆分后可维护性显著提升；④ HF 导出从“源码污染根目录”变为“构建产物”。

七、建议执行顺序

1) 阶段 0 卫生 + 测试基线 → 2) 阶段 1 单命名空间 / src 布局 / 修 HF 死路径（这一步直接解决“不能 pip 安装”）→ 3) 验证 pip install -e . 与全量测试 → 4) 阶段 2 分层与巨石拆分 → 5) 阶段 3 护栏。

阶段 1 完成即达成你最核心的诉求（可安装 + 有命名空间边界）；阶段 2 解决“不优雅、没层次”。
